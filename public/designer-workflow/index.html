Part 0Before you start

This guide is the day-to-day: sit down, build something, get it in front of the team. It assumes your machine is already set up.

First time on this project? Go to Contributing to the dashboard.

Most Important Thing. You work on YOUR BRANCH. Never push directly to main.If you ever find yourself on main, stop and tell Jill.

Part 1Every time you sit down

Open Claude → the Code tab → the xcel-ux-dashboard folder. Start a new conversation for each piece of work.

How to talk to it

  1. Plain sentences, one step at a time. One request to a message, not three:

    YOURebase my branch onto main.

  2. Read the line before, and the summary after. Claude says what it is about to do, then what it did. If either surprises you, ask before going on.

  3. Allow the permission card when it matches what you asked for. If it describes something else, click Deny and ask what it was trying to do.

  4. A refusal naming a file is correct. That file is the Hub's own machinery and only Jill changes it. Tell her what you needed.

  5. Type / for the routines. Yours are /promote-component, /share-branch and /promote-to-prototype — Part 8 says what each one does.

Then ask one question

YOUWhich branch am I on, do I have uncommitted changes, and how far behind main am I?

Your own feat/… branch, changes you recognise, under ten commits behind — go. Anything else:

  • On main — stop and tell Jill.
  • Changes you do not recognise — ask Claude what they are before touching anything.
  • Ten or more behind — rebase before you build (Part 2).

Rebasing every few days is painless. Rebasing once at the end of a month is not.

Part 2Keeping your branch current

Main moves under you — several times a week at the moment. A rebase replays your commits on top of today's main, as if you had started this morning. It does not change your work.

Rebase every few days.Three days behind is a minute's work; a month behind is an afternoon.

Most days it is one sentence

YOUCommit anything uncommitted, make a backup branch, then fetch origin and rebase this branch onto origin/main. Run the build and the tests, then push with force-with-lease. If anything conflicts, stop and show me both sides.

Allow it. The backup means nothing that follows can lose work — you can delete it next week. Expect it to stop if main has edited the same files you have: that is the normal case when two people work on one surface, and the next heading is what to do about it.

Commits of yours that already reached main in another form — through someone else's promotion, say — are recognised and dropped on the way. Coming out with fewer commits than you went in with is normal, not lost work.

If it stops on a conflict

Claude names the file and shows two versions of the same lines: what main has, and what your commit has. Read both, then say one of:

YOUKeep my version.  /  Keep main's version.  /  Keep both — main's block first, then mine.
YOUContinue the rebase.

It may stop again on the next commit; do the same thing. If you cannot tell which to keep, say "Abort the rebase" — your branch goes back exactly as it was — and ask Jill.

Then look at it

YOUHow far behind main am I now, and what is the review link?

You want 0 behind. Netlify takes two to four minutes to build, and the deploys page shows where it is up to. Click through from the page a reviewer would start on: if it looks like it did before the rebase, you are done. If something that used to work is broken, that is where main and your branch disagree — tell Jill which page.

Or have Claude do all of this for you every weekday morning — Part 9.

Part 3Building a change, start to finish

This is the loop you will repeat for every piece of work. Each step is one sentence to Claude.

  1. Start from main.
    YOUFetch origin, then make a new branch called feat/short-name from origin/main and switch to it.

    Never branch from an old branch of yours; it drags the old branch's history along.

  2. Say what you want.

    Describe the change as you would to a developer sitting next to you. Name the page, the component, what it should do instead. Claude reads the code and proposes where the change goes. If it names a file you don't recognise, ask "What is that file?" before saying yes.

  3. Changing something that already exists? Use a sibling copy.
    YOU/promote-component

    Name the component. It copies StudyPaceTile.tsx to StudyPaceTileV2.tsx, leaves the original untouched, and adds a flag that picks between them. This is why your branch almost never conflicts with anyone else's: nobody edits the same file.

  4. The flag is on by default on your branch.

    Claude does this when you say "behind a feature flag that is on by default on this branch". It means your branch build shows your version, and Jill can decide at merge whether it ships. Ask "What is the flag called?" and write it down; the review link can turn it off with &ff=flag-name:off if you want to show the before.

  5. Check it.
    YOURun the type check, the tests, and lint on the files I changed.

    If you added or edited anything under public/prototypes/, add "and the smoke suites". Red means fix before pushing: "Fix that and run it again."

  6. Commit.
    YOUCommit everything on this branch with a message that says what changed and why.

    Claude writes the message in the project's style and shows it to you first.

  7. Push.
    YOUPush my branch to GitHub.

    The first push on a new branch also sets it up on GitHub; Claude handles that. From then on, every push is the same sentence.

  8. Wait for Netlify.

    Two to four minutes. If you want to know rather than guess:

    YOUCheck whether my branch has finished building on Netlify.

    Or watch it yourself: the deploys page lists every branch build, newest first, with Building, Published or Failed on each. Find yours by branch name. You need to be signed in to the Netlify project — ask Jill if you are not on it.

  9. Get the link.
    YOUGive me the review link for this branch.

    The shape is https://‹branch-with-dashes›--ux-design-xceldashboard.netlify.app followed by the page: /dashboard-rebrand?demo=1 for the dashboard, /dashboard-rebrand?demo=1&section=compass for Compass, /end-to-end-demo?demo=1 for the invite flow. ?demo=1 turns on the demo controls bar.

  10. Look at it the way a reviewer would.

    Click through from the page they would start on, not straight to your component. Three bugs in September were invisible on a direct link and obvious on the first click.

  11. Keep going.

    Each further change is step 2, then /share-branch again. Rebase every few days (Part 2) so the final merge is boring. When the next change is really a different piece of work, start a new branch for it rather than letting this one grow.

Steps 5 to 9 are one command. /share-branch runs the checks, commits, pushes, waits for the build and hands you the link, then opens the Refinement form — Part 4. The long way above is what it is doing, which is worth knowing for the day it stops halfway.

Part 4Sharing on Refinement

Refinement is the board where work under discussion lives. Anyone adds to it, nothing on it is the source of truth, it filters by your name, and it has an archive.

A row is one chunk of work, not a branch you live on. Since 15 October rows group under the feature they are chunks of, newest first. When a new chunk carries on from an older one, the older one folds under "1 earlier chunk" — still there, still clickable — so a feature keeps a history you can open in a review. One long-running branch gives you a single link and no history at all.

Finish a chunk, share it, start a new branch for the next.That is the habit the board is built around, and the reason small branches pay you back.

Adding your branch, the quick way

  1. On your branch in the Code tab:

    YOU/share-branch

    It was called /promote-to-refinement until 15 October, and that name still works. It was briefly /share — but that name belongs to Claude Code itself, so the skill never loaded, which is why it is /share-branch now.

  2. Claude asks once — checks, commit, push, open the form? — then runs the type check and the tests, commits anything uncommitted, pushes, waits for Netlify to build your branch, works out its address and a title, and asks what feature this is a chunk of. Nothing reaches the board or the To Do Board until you click the button on each of the two forms it opens.

  3. In the form, Added by is a pick-list of the five of you. Pick your own name. The product (Atlas, Compass, Both) is already chosen from what your branch touched; change it if it is wrong.

    Feature is what this chunk is part of — start typing and the features already on the board are offered, so take one if it fits. Replaces appears only when that feature already has chunks, and defaults to your own newest one; its first option, Nothing — these sit side by side, is the right answer when two treatments should both stay up.

  4. Click Add link. Your row appears at the top of its feature group, showing your name, when it was last saved, and the product.

  5. Then the card.

    The To Do Board's card sheet opens next, also filled in, in the Ready For Refinement column — the row is the thing to look at, the card is who is waiting on it. Click Add card. If this chunk already has a card on the board, say so and Claude asks rather than opening a second one. Then it offers to cut your next branch.

Adding it by hand. Open the Hub, click Refinement, click Add link, paste the review link from Part 3, type a title and a one-line note on what to look at, pick your name, pick the product, name the feature, Save.

Finding things. The pills above the list are the five names: All, Jill, Anjani, Eric, Afsana, Cody (the roster says Jill, which is what she signs). Click a name to see only that person's rows; click it again to clear. There is no product pill any more; the product is the tag on the row. Rows sit under their feature heading, so looking for a piece of work means looking for its name rather than its branch.

When a row's discussion is over

You want toDo thisWhat happens
Tidy it off the board but keep itClick the row's ⋮, choose ArchiveThe row disappears from the board. It is stamped with when and by whom. Nothing is deleted.

Bring one backIn the archive, click its ⋮, choose UnarchiveIt is back on the board. Anyone can do this.

Use Archive by default. Remove is for mistakes.

Two things to know. The Updated tag changes only when the row is saved, not when your branch changes; after a big push, open the row and Save it again so the team sees fresh activity. And a Refinement row follows main underneath: if a component you point at changes on main, the row changes with it. Anything that must stay frozen, a user test for instance, is Jill's /promote-to-testing, not a Refinement row.

Part 5Making your surface the prototype, and who ships it

Prototypes is the one section that means "this is the product". It holds one row per surface, every row is main's build, and each surface has an owner who decides what it should be.

End-to-End User ExperienceJillheld back — the row is a placeholder, but the build is still at /dashboard-rebrand?demo=1

Atlas LearningEric/dashboard-rebrand?demo=1&section=dashboard
Compass LearningAnjani/dashboard-rebrand?demo=1&section=compass
Admin ToolCodyplaceholder until it is built

There are two separate decisions, made by two different people:

  • What the surface should be is the owner's call, and the owner records it by running the promotion on their own branch.
  • When it reaches main is Jill's call, and only she can do it.

When your branch is what your surface should become

  1. Make sure the branch is current (Part 2) and the review link looks right.

  2. On your branch, name your scope: "for Compass" (Anjani), "for Atlas Learning" or "for Invite & Purchase" (Eric).

    YOU/promote-to-prototype for Compass

  3. Claude lists the flags your branch introduced and asks, for each, whether it should be the default. Say yes to the ones that are your design and no to anything experimental you are not ready to stand behind.

  4. It commits those defaults on your branch. Nothing has reached a stakeholder yet; this is a decision written down, not a release.

  5. YOUPush my branch.

  6. Tell Jill, in words: "My Compass branch feat/… is ready to ship." Include the review link.

  7. Jill runs ship-to-main. It refuses a branch whose owner has not run step 2, so the order matters.

  8. A few minutes after she ships, your surface's row on Prototypes is your work. Its Updated tag changes to that moment.

  9. Archive your Refinement row (Part 4), since the board is for things under discussion and this one is decided.

  10. Start the next piece from a fresh branch off main (Part 3, step 1). Do not keep working on the shipped branch.

If you own the surface, you can also decide something should NOT go in. Say so, archive the Refinement row, and tell Jill; she has a routine that records why a branch was tried and declined.

Part 9Scheduled routines

Claude Code can run a job on a schedule: you describe it once and it runs in your project folder, in a fresh session, and sends you a note when it is done. Two are worth having — a rebase every weekday morning, and a sweep for old backup branches on Fridays.

Two things to know about either of them:

  • It runs while the Claude app is open. If your laptop was closed at 8:30, it runs the next time you open the app. In practice that means "when I start my day".
  • It works on whichever branch is checked out in your xcel-ux-dashboard folder. That is the branch you were on when you closed the app yesterday, which is almost always the one you want.

The morning rebase

It makes Part 2 something that happens while you get coffee. Open the Code tab on the project and paste this, exactly:

Paste to Claude

Create a scheduled task called morning-rebase that runs every weekday at 8:30 in this project folder. Each run, do the following and nothing else:

  1. Report the current branch. If it is main, or there is no branch checked out, stop and say so.
  2. If there are uncommitted changes, stop and say so. Do not stash them and do not commit them.
  3. Fetch origin. If the branch is zero commits behind origin/main, report "already current" and stop.
  4. Create a local backup branch named backup/‹branch›/‹today's date› pointing at the current commit. Do not push it.
  5. Rebase the branch onto origin/main. If any file conflicts, abort the rebase so the branch is exactly as it was, and report which files conflicted and in which commit.
  6. If the rebase succeeded, run npm run build and then npx vitest run. If either fails, do not push. Report what failed; say that the local branch is rebased but origin still has yesterday's version.
  7. If both passed, push the branch to origin with --force-with-lease. Never push main. Never push without the lease.
  8. Finish with a six-line summary: the branch; how many commits behind it was; whether there were conflicts; whether build and tests passed; whether it pushed; and the Netlify review link for the branch.

Never run git switch main, never edit files, never resolve a conflict yourself, and never delete anything.

Claude confirms the schedule and the task name. Say yes.

What you see each morning

A short note in the Claude app: rebased and pushed, or stopped and why. If it says it stopped on a conflict, do it by hand — Part 2, "If it stops on a conflict". If it says checks failed, open the Code tab and say:

YOUShow me what failed in the morning rebase.

The Friday backup sweep

Every rebase leaves a backup/… branch behind — the morning task makes one too. They are cheap to keep and easy to forget, and after a month there are twenty. This one finds the ones that have done their job. It does not delete anything.

Paste to Claude

Create a scheduled task called backup-sweep that runs every Friday at 16:00 in this project folder. Each run, do the following and nothing else:

  1. List every local branch whose name starts with backup/, and every branch on origin whose name starts with backup/. Match on the prefix only — the rest of the name is not a fixed shape.
  2. For each one report: its name, how many days old its newest commit is, the branch it was made from, and whether that branch still exists locally and on origin.
  3. Sort them into two lists. Delete nothing.
    • Safe to delete — older than fourteen days, AND the branch it was made from still exists, AND that branch has no commits that are missing from origin.
    • Keep — everything else, with the reason on each: too new, the branch it backed up is gone, or that branch has work that has not been pushed.
  4. If a backup's source branch no longer exists anywhere, say so loudly and put it in Keep: that backup may be the only copy of the work.
  5. Finish with the exact command that would delete the safe ones, local and remote listed separately, and stop there. Never delete a branch, local or on origin, unless I say yes in that conversation.

Never touch a branch that is not named backup/…, never push, and never run git switch.

Read the two lists, and if you agree, say so:

YOUDelete the backups you listed as safe, local and remote.

Why it asks rather than decides. A rebase rewrites your commits, so a backup is never "merged" in git's sense and git branch -d will refuse it — deleting one needs the force form, -D. That is exactly what the backup was for, which is also why nothing here deletes on your behalf. If you are ever unsure about one, keep it: a stale branch costs nothing.
