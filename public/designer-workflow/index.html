Part 0Before you start

This guide is the day-to-day: sit down, build something, get it in front of the team. It assumes your machine is already set up.

First time on this project? Go to Contributing to the dashboard first — it covers the accounts, the clone, the dependencies and putting your name on your commits, and it has the shape of the whole loop in one picture. Come back here once "Which branch am I on?" gets a sensible answer. The vocabulary — main, branch, commit, push, rebase, merge — is in that guide too, and in Part 10 below.

When a step shows a sentence in a speech bubble, that is exactly what you type to Claude. You do not need to know a single git command; Claude knows them.

You work on your branch. Jillienne works on main.If you ever find yourself on main, stop and tell her.

Part 1Every time you sit down

Opening up. Open the Claude app, go to the Code tab, and make sure the folder shown is xcel-ux-dashboard. Start a new conversation for each piece of work. Old conversations are fine to leave.

How to talk to it

  1. Type plain sentences, one step at a time. "Rebase my branch onto main" is better than three requests in one message.

  2. Claude tells you what it is about to do before it does it. Read that line.

  3. Before it runs a command or changes a file, a permission card appears with Allow and Deny. Click Allow when the card describes the thing you asked for. If it describes something you did not ask for, click Deny and ask what it was trying to do.

  4. If Claude refuses to edit a file and names it, that refusal is correct. Those files are the Hub's own machinery and only Jillienne changes them. Tell her what you needed.

  5. Typing / in the chat box shows the project's ready-made routines. The ones you will use are /promote-component, /share and /promote-to-prototype. Each one asks you questions and does the steps. Part 8 says what each one asks, what it does, and when to reach for it.

  6. When Claude finishes, it summarises what it did. If anything in that summary surprises you, ask before going on.

The three questions to ask before touching anything

AskA good answer sounds likeIf not
"Which branch am I on, and do I have uncommitted changes?"Your feat/… branch, and either "no changes" or a list you recognise.On main: stop, tell Jillienne. Changes you don't recognise: ask Claude what they are first.
"Fetch origin. How far behind main is my branch?"A number of commits. Under ten is fine for now.Ten or more: rebase before building anything new (Part 2 shows how).

Rebasing every few days is painless. Rebasing once at the end of a month is not.

Part 2Keeping your branch current

Main moves under you — several times a week at the moment. A rebase replays your commits on top of today's main, as if you had started this morning. It does not change your work.

Do it every few days. Rebasing a branch that is three days behind is a minute's work; rebasing one that is a month behind is an afternoon, and it is the same ten steps either way.

Do them one sentence at a time and wait for each answer.

  1. Confirm where you are.
    YOUWhich branch am I on, and do I have uncommitted changes?

    You want your own feat/… branch. If you are somewhere else, switch to it before anything else.

  2. Save anything loose.

    If step 1 listed changes:

    YOUCommit everything on this branch with a message that says what it is.

    A rebase moves commits; it cannot move work you have not committed.

  3. Make a safety copy.
    YOUCreate a backup branch called backup/‹my-branch›-‹today's date› pointing at where I am now, and push it.

    Now nothing you do next can lose work. You can delete it next week.

  4. Do the rebase.
    YOUFetch origin and rebase this branch onto origin/main. If anything conflicts, stop and show me both sides before changing anything.

    Allow it. Expect it to stop if main has edited the same files you have — which is the normal case when two people are working on one surface, and exactly what step 5 is for.

    Commits of yours that already reached main in another form — through someone else's promotion, say — are recognised and dropped during the rebase. Your branch coming out with fewer commits than it went in with is normal, not lost work.

  5. If it stops on a conflict.

    Claude says a file name and shows two versions of the same lines: what main has, and what your commit has. Read both. Then say one of:

    YOUKeep my version.  /  Keep main's version.  /  Keep both — main's block first, then mine.
    YOUContinue the rebase.

    It may stop again on the next commit; do the same thing. If you cannot tell which to keep, say "Abort the rebase". Your branch goes back exactly as it was. Then ask Jillienne.

  6. Confirm it worked.
    YOUHow far behind main is my branch now, and how many commits ahead?

    You want 0 behind. The number ahead is your own work, minus anything that had already reached main.

  7. Check the build.
    YOURun the build, the tests, and lint on the files I changed.

    The build is the gate Netlify uses; if it fails here, your branch will not deploy. If something fails, read Claude's summary and say "Fix that and run it again." If it is in a file you never touched, stop and ask Jillienne.

  8. Push.
    YOUPush my rebased branch. It will need a force push with lease.

    A rebase rewrites your branch's history, so a normal push is refused with a message about the branch being behind. Force-with-lease is the safe form: it refuses if someone else pushed to your branch in the meantime. This is normal on your own branch and is never done on main.

  9. Get the link.
    YOUGive me the Netlify review link for this branch.

    Netlify starts building the moment you push and takes two to four minutes. The page asks for the same password as the Hub.

  10. Look at it.

    Click through from the page a reviewer would start on. If it looks like it did before the rebase, you are done. If something that used to work is broken, that is where main and your branch disagree; tell Jillienne which page.

After the first one, rebasing is usually just steps 4, 7 and 8. Or let Claude do it for you every weekday morning — Part 9.

Part 3Building a change, start to finish

This is the loop you will repeat for every piece of work. Each step is one sentence to Claude.

  1. Start from main.
    YOUFetch origin, then make a new branch called feat/short-name from origin/main and switch to it.

    Never branch from an old branch of yours; it drags the old branch's history along.

  2. Say what you want.

    Describe the change as you would to a developer sitting next to you. Name the page, the component, what it should do instead. Claude reads the code and proposes where the change goes. If it names a file you don't recognise, ask "What is that file?" before saying yes.

  3. Changing something that already exists? Use a sibling copy.
    YOU/promote-component

    Name the component. It copies StudyPaceTile.tsx to StudyPaceTileV2.tsx, leaves the original untouched, and adds a flag that picks between them. This is why your branch almost never conflicts with anyone else's: nobody edits the same file.

  4. The flag is on by default on your branch.

    Claude does this when you say "behind a feature flag that is on by default on this branch". It means your branch build shows your version, and Jillienne can decide at merge whether it ships. Ask "What is the flag called?" and write it down; the review link can turn it off with &ff=flag-name:off if you want to show the before.

  5. Check it.
    YOURun the type check, the tests, and lint on the files I changed.

    If you added or edited anything under public/prototypes/, add "and the smoke suites". Red means fix before pushing: "Fix that and run it again."

  6. Commit.
    YOUCommit everything on this branch with a message that says what changed and why.

    Claude writes the message in the project's style and shows it to you first.

  7. Push.
    YOUPush my branch to GitHub.

    The first push on a new branch also sets it up on GitHub; Claude handles that. From then on, every push is the same sentence.

  8. Wait for Netlify.

    Two to four minutes. If you want to know rather than guess:

    YOUCheck whether my branch has finished building on Netlify.
  9. Get the link.
    YOUGive me the review link for this branch.

    The shape is https://‹branch-with-dashes›--ux-design-xceldashboard.netlify.app followed by the page: /dashboard-rebrand?demo=1 for the dashboard, /dashboard-rebrand?demo=1&section=compass for Compass, /end-to-end-demo?demo=1 for the invite flow. ?demo=1 turns on the demo controls bar.

  10. Look at it the way a reviewer would.

    Click through from the page they would start on, not straight to your component. Three bugs in September were invisible on a direct link and obvious on the first click.

  11. Keep going.

    Each further change is step 2, then /share again. Rebase every few days (Part 2) so the final merge is boring. When the next change is really a different piece of work, start a new branch for it rather than letting this one grow.

Steps 5 to 9 are one command. /share runs the checks, commits, pushes, waits for the build and hands you the link, then opens the Refinement form — Part 4. The long way above is what it is doing, which is worth knowing for the day it stops halfway.

What you never do: run the site on your own computer, edit main, or edit the Hub's own files. Claude will refuse and name them; ask Jillienne.

Part 4Sharing on Refinement

Refinement is the board where work under discussion lives. Anyone adds to it, nothing on it is the source of truth, it filters by your name, and it has an archive.

A row is one chunk of work, not a branch you live on. Since 15 October rows group under the feature they are chunks of, newest first. When a new chunk carries on from an older one, the older one folds under "1 earlier chunk" — still there, still clickable — so a feature keeps a history you can open in a review. One long-running branch gives you a single link and no history at all.

Finish a chunk, share it, start a new branch for the next.That is the habit the board is built around, and the reason small branches pay you back.

Adding your branch, the quick way

  1. On your branch in the Code tab:

    YOU/share

    It was called /promote-to-refinement until 15 October, and that name still works.

  2. Claude asks once — checks, commit, push, open the form? — then runs the type check and the tests, commits anything uncommitted, pushes, waits for Netlify to build your branch, works out its address and a title, and asks what feature this is a chunk of. Nothing reaches the board until you click Save.

  3. In the form, Added by is a pick-list of the five of you. Pick your own name. The product (Atlas, Compass, Both) is already chosen from what your branch touched; change it if it is wrong.

    Feature is what this chunk is part of — start typing and the features already on the board are offered, so take one if it fits. Replaces appears only when that feature already has chunks, and defaults to your own newest one; its first option, Nothing — these sit side by side, is the right answer when two treatments should both stay up.

  4. Click Save. Your row appears at the top of its feature group, showing your name, when it was last saved, and the product. Claude then offers to cut your next branch.

Adding it by hand. Open the Hub, click Refinement, click Add link, paste the review link from Part 3, type a title and a one-line note on what to look at, pick your name, pick the product, name the feature, Save.

Finding things. The pills above the list are the five names: All, Jillienne, Anjani, Eric, Afsana, Cody. Click a name to see only that person's rows; click it again to clear. There is no product pill any more; the product is the tag on the row. Rows sit under their feature heading, so looking for a piece of work means looking for its name rather than its branch.

When a row's discussion is over

You want toDo thisWhat happens
Tidy it off the board but keep itClick the row's ⋮, choose ArchiveThe row disappears from the board. It is stamped with when and by whom. Nothing is deleted.

Use Archive by default. Remove is for mistakes.

Two things to know. The Updated tag changes only when the row is saved, not when your branch changes; after a big push, open the row and Save it again so the team sees fresh activity. And a Refinement row follows main underneath: if a component you point at changes on main, the row changes with it. Anything that must stay frozen, a user test for instance, is Jillienne's /promote-to-testing, not a Refinement row.

Part 5Making your surface the prototype, and who ships it

Prototypes is the one section that means "this is the product". It holds one row per surface, every row is main's build, and each surface has an owner who decides what it should be.

There are two separate decisions, made by two different people:

  • What the surface should be is the owner's call, and the owner records it by running the promotion on their own branch.
  • When it reaches main is Jillienne's call, and only she can do it.

When your branch is what your surface should become

  1. Make sure the branch is current (Part 2) and the review link looks right.

  2. On your branch, name your scope: "for Compass" (Anjani), "for Atlas Learning" or "for Invite & Purchase" (Eric).

    YOU/promote-to-prototype for Compass

  3. Claude lists the flags your branch introduced and asks, for each, whether it should be the default. Say yes to the ones that are your design and no to anything experimental you are not ready to stand behind.

  4. It commits those defaults on your branch. Nothing has reached a stakeholder yet; this is a decision written down, not a release.

  5. YOUPush my branch.

  6. Tell Jillienne, in words: "My Compass branch feat/… is ready to ship." Include the review link.

  7. Jillienne runs ship-to-main. It refuses a branch whose owner has not run step 2, so the order matters.

  8. A few minutes after she ships, your surface's row on Prototypes is your work. Its Updated tag changes to that moment.

  9. Archive your Refinement row (Part 4), since the board is for things under discussion and this one is decided.

  10. Start the next piece from a fresh branch off main (Part 3, step 1). Do not keep working on the shipped branch.

If you own the surface, you can also decide something should NOT go in. Say so, archive the Refinement row, and tell Jillienne; she has a routine that records why a branch was tried and declined.

Part 9The morning auto-rebase

You can have Claude rebase your branch for you every weekday morning, so Part 2 becomes something that happens while you get coffee.

Claude Code has scheduled tasks: you describe the job once, and it runs it in your project folder on a schedule, in a fresh session, and sends you a note when it is done. Two things to know first:

  • It runs while the Claude app is open. If your laptop was closed at 8:30, it runs the next time you open the app. In practice that means "when I start my day".
  • It works on whichever branch is checked out in your xcel-ux-dashboard folder. That is the branch you were on when you closed the app yesterday, which is almost always the one you want.

Set it up once

Open the Code tab on the project and paste this, exactly:

Paste to Claude

Create a scheduled task called morning-rebase that runs every weekday at 8:30 in this project folder. Each run, do the following and nothing else:

  1. Report the current branch. If it is main, or there is no branch checked out, stop and say so.
  2. If there are uncommitted changes, stop and say so. Do not stash them and do not commit them.
  3. Fetch origin. If the branch is zero commits behind origin/main, report "already current" and stop.
  4. Create a local backup branch named backup/‹branch›/‹today's date› pointing at the current commit. Do not push it.
  5. Rebase the branch onto origin/main. If any file conflicts, abort the rebase so the branch is exactly as it was, and report which files conflicted and in which commit.
  6. If the rebase succeeded, run npm run build and then npx vitest run. If either fails, do not push. Report what failed; say that the local branch is rebased but origin still has yesterday's version.
  7. If both passed, push the branch to origin with --force-with-lease. Never push main. Never push without the lease.
  8. Finish with a six-line summary: the branch; how many commits behind it was; whether there were conflicts; whether build and tests passed; whether it pushed; and the Netlify review link for the branch.

Never run git switch main, never edit files, never resolve a conflict yourself, and never delete anything.

Claude confirms the schedule and the task name. Say yes.

What you see each morning

A short note in the Claude app: rebased and pushed, or stopped and why. If it says it stopped on a conflict, do Part 2 step 5 by hand. If it says checks failed, open the Code tab and say:

YOUShow me what failed in the morning rebase.
