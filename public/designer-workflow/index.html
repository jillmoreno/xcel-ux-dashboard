01Before you start

There are three places, and it helps to know which one you are looking at:

Six words you will see over and over:

WordPlain meaning

The one rule under everything

You work on your branch, Jillienne works on main. If you ever find yourself on main, stop and tell her.

02One-time setup

Do this once per computer. It takes about twenty minutes, most of it waiting.

1Install the Claude desktop app

Download it from claude.ai and sign in with the account Jillienne invited. Claude Code is the Code tab inside that app. It is a chat window that can also read and change files on your computer.

2Make an empty folder

On your computer, called xcel. Documents is fine.

3Open the Code tab

It asks which folder to work in. Pick the xcel folder you just made.

4Get the code

In the chat box, type: "Clone https://github.com/jillmoreno/xcel-ux-dashboard into this folder." Claude will show you the command it wants to run and ask for permission. Click Allow. If a browser window opens asking you to sign in to GitHub, sign in as yourself (Anjani is Anjanisatya5, Eric is EnormanColibri). You are both already collaborators on the repository.

5Point Claude at the project

The clone made a folder inside xcel called xcel-ux-dashboard. Use the Code tab's folder picker to open that inner folder. From now on, every session starts by opening this folder.

6Install what the project needs

Type: "Install the project's dependencies." Allow it. This downloads about a minute's worth of packages. If Claude says Node or npm is not installed, type: "Install Node LTS for me, then install the dependencies." Allow each step.

7Put your name on your work

Type, with your own details: "For this project, set my git name to Anjani Satya and my git email to the address on my GitHub account." Eric: "Eric Norman" and eric.norman@simplenursing.com.

This matters more than it looks. The Hub decides who owns a change by who authored it, and Anjani's earlier commits were recorded as written by Claude because this was never set.

8Check it

Type: "Which branch am I on, and what are my git name and email?" You should hear main and your own name. That is the only time being on main is fine, because you have not changed anything yet.

You do not install Netlify, Vite, or anything else by hand. You do not run the site on your own computer. The branch build on Netlify is your preview.

03Every time you sit down

Opening up. Open the Claude app, go to the Code tab, and make sure the folder shown is xcel-ux-dashboard. Start a new conversation for each piece of work. Old conversations are fine to leave.

How to talk to it.

  1. Type plain sentences, one step at a time. "Rebase my branch onto main" is better than three requests in one message.
  2. Claude tells you what it is about to do before it does it. Read that line.
  3. Before it runs a command or changes a file, a permission card appears with Allow and Deny. Click Allow when the card describes the thing you asked for. If it describes something you did not ask for, click Deny and ask what it was trying to do.
  4. If Claude refuses to edit a file and names it, that refusal is correct. Those files are the Hub's own machinery and only Jillienne changes them. Tell her what you needed.
  5. Typing / in the chat box shows the project's ready-made routines. The ones you will use are /promote-component, /share and /promote-to-prototype. Each one asks you questions and does the steps. Section 11 says what each one asks, what it does, and when to reach for it.
  6. When Claude finishes, it summarises what it did. If anything in that summary surprises you, ask before going on.

The three questions to ask before touching anything.

AskWhat a good answer sounds likeIf not
"Which branch am I on, and do I have uncommitted changes?"Your feat/… branch, and either "no changes" or a list you recognise.On main: stop, tell Jillienne. Changes you don't recognise: ask Claude what they are before anything else.
"Fetch origin. How far behind main is my branch?"A number of commits. Under ten is fine for now.Ten or more: rebase before building anything new (section 04 shows how).
"Has anything on main changed the files I'm working on?""No", or a short list.A list: read it, because that is where a conflict would come from later.

Rebasing every few days is painless. Rebasing once at the end of a month is not.

04Eric: rebase feat/atlas-compass-global-nav

A snapshot, not a standing instruction

The numbers in this section were true on the evening of 15 October 2026. The ten steps are the general recipe and stay right; the counts will not. Re-ask Claude "how far behind main is my branch?" rather than trusting the figures below.

As of that evening your branch has 10 commits that are not on main (the checkout payment rework, the product-detail rail, the Home styling, the password walk-through), and main has moved 74 commits past where you started. Four of your ten already reached main that afternoon in another form, through Jillienne's invite promotion; git will recognise those and drop them during the rebase, which is normal. Those 67 include the one-site change, the new Hub nav, and Anjani's second Compass master. Your branch needs to be moved on top of all that before anything else happens to it.

A rebase does not change your work. It replays your commits, one at a time, on top of today's main, as if you had started this morning. Do it one sentence at a time and wait for each answer.

1Confirm where you are

"Which branch am I on, and do I have uncommitted changes?" You want to hear feat/atlas-compass-global-nav. If you are somewhere else: "Switch to feat/atlas-compass-global-nav."

2Save anything loose

If step 1 listed changes: "Commit everything on this branch with a message that says what it is." A rebase moves commits; it cannot move work you have not committed.

3Make a safety copy

"Create a backup branch called backup/atlas-compass-global-nav-oct-15 pointing at where I am now, and push it." Now nothing you do next can lose work. You can delete it next week.

4Do the rebase

"Fetch origin and rebase this branch onto origin/main. If anything conflicts, stop and show me both sides before changing anything." Allow it.

Expect it to stop at least once this time: main took your morning's Confirmation page and added a flag to it (the flow now ends at a loading page), and your afternoon commits edit the same three files — InvitedCheckoutPage, InvitedConfirmationPage, InvitedProductDetailPage. That is exactly the case step 5 is for.

5If it stops on a conflict

Claude will say a file name and show two versions of the same lines: what main has, and what your commit has. Read both. Then say one of: "Keep my version", "Keep main's version", or "Keep both — main's block first, then mine." Then: "Continue the rebase." It may stop again on the next commit; do the same thing.

If you cannot tell which to keep, say "Abort the rebase" — your branch goes back exactly as it was — and ask Jillienne.

6Confirm it worked

"How far behind main is my branch now, and how many commits ahead?" You want: 0 behind, and about 5 or 6 ahead (the four commits main already had will have dropped out).

7Check the build

"Run the build, the tests, and lint on the files I changed." The build is the gate Netlify uses; if it fails here, your branch will not deploy. If something fails, read Claude's summary and say "Fix that and run it again." If it is in a file you never touched, stop and ask Jillienne.

8Push

"Push my rebased branch. It will need a force push with lease." A rebase rewrites your branch's history, so a normal push is refused with a message about the branch being behind. Force-with-lease is the safe form: it refuses if someone else pushed to your branch in the meantime. This is normal on your own branch and is never done on main.

9Get the link

"Give me the Netlify review link for this branch at the invite flow." It is https://feat-atlas-compass-global-nav--ux-design-xceldashboard.netlify.app/end-to-end-demo?demo=1. Netlify starts building the moment you push and takes two to four minutes. The page asks for the same password as the Hub.

10Look at it

Click through the invite flow from the start, the way a reviewer would. If it looks like it did before the rebase, you are done. If something that used to work is broken, that is where main and your branch disagree; tell Jillienne which page.

From here your branch is current. Rebase again every few days with steps 4, 7 and 8; it will be quicker each time. Or let Claude do it for you every morning (section 12).

06Building a change, start to finish

This is the loop you will repeat for every piece of work. Each step is one sentence to Claude.

1Start from main

"Fetch origin, then make a new branch called feat/‹short-name› from origin/main and switch to it." Never branch from an old branch of yours; it drags the old branch's history along.

2Say what you want

Describe the change as you would to a developer sitting next to you. Name the page, the component, what it should do instead. Claude reads the code and proposes where the change goes. If it names a file you don't recognise, ask "What is that file?" before saying yes.

3Changing something that already exists? Use a sibling copy

Say /promote-component and name the component. It copies StudyPaceTile.tsx to StudyPaceTileV2.tsx, leaves the original untouched, and adds a flag that picks between them. This is why your branch almost never conflicts with anyone else's: nobody edits the same file.

4The flag is on by default on your branch

Claude does this when you say "behind a feature flag that is on by default on this branch". It means your branch build shows your version, and Jillienne can decide at merge whether it ships. Ask Claude "What is the flag called?" and write it down; the review link can turn it off with &ff=flag-name:off if you want to show the before.

5Check it

"Run the type check, the tests, and lint on the files I changed." If you added or edited anything under public/prototypes/, add "and the smoke suites". Red means fix before pushing: "Fix that and run it again."

6Commit

"Commit everything on this branch with a message that says what changed and why." Claude writes the message in the project's style and shows it to you first.

7Push

"Push my branch to GitHub." The first push on a new branch also sets it up on GitHub; Claude handles that. From then on, every push is the same sentence.

8Wait for Netlify

Two to four minutes. "Check whether my branch has finished building on Netlify" if you want to know rather than guess.

9Get the link

"Give me the review link for this branch." The shape is https://‹branch-with-dashes›--ux-design-xceldashboard.netlify.app followed by the page: /dashboard-rebrand?demo=1 for the dashboard, /dashboard-rebrand?demo=1&section=compass for Compass, /end-to-end-demo?demo=1 for the invite flow. ?demo=1 turns on the demo controls bar.

10Look at it the way a reviewer would

Click through from the page they would start on, not straight to your component. Three bugs in September were invisible on a direct link and obvious on the first click.

11Keep going

Each further change is step 2, then /share again. Rebase every few days (section 04, steps 4 to 8) so the final merge is boring. When the next change is really a different piece of work, start a new branch for it rather than letting this one grow.

Steps 5 to 9 are one command

/share runs the checks, commits, pushes, waits for the build and hands you the link, then opens the Refinement form — section 07. The long way above is what it is doing, which is worth knowing for the day it stops halfway.

What you never do

Run the site on your own computer, edit main, or edit the Hub's own files — Claude will refuse and name them. Ask Jillienne.

07Sharing on Refinement

Refinement is the board where work under discussion lives. Anyone adds to it, nothing on it is the source of truth, it filters by your name, and it has an archive.

A row is one chunk of work, not a branch you live on. Since 15 October rows group under the feature they are chunks of, newest first. When a new chunk carries on from an older one, the older one folds under "1 earlier chunk" — still there, still clickable — so a feature keeps a history you can open in a review. One long-running branch gives you a single link and no history at all. That is the whole reason to work in small pieces: finish one, share it, start a new branch for the next.

Adding your branch, the quick way.

  1. On your branch in the Code tab, type /share. It was called /promote-to-refinement until 15 October, and that name still works.
  2. Claude asks once — checks, commit, push, open the form? — then runs the type check and the tests, commits anything uncommitted, pushes, waits for Netlify to build your branch, works out its address and a title, and asks what feature this is a chunk of. Nothing reaches the board until you click Save.
  3. In the form, Added by is a pick-list of the five of you. Pick your own name. The product (Atlas, Compass, Both) is already chosen from what your branch touched; change it if it is wrong. Feature is what this chunk is part of — start typing and the features already on the board are offered, so take one if it fits. Replaces appears only when that feature already has chunks, and defaults to your own newest one; its first option, Nothing — these sit side by side, is the right answer when two treatments should both stay up.
  4. Click Save. Your row appears at the top of its feature group, showing your name, when it was last saved, and the product. Claude then offers to cut your next branch.

Adding it by hand. Open the Hub, click Refinement, click Add link, paste the review link from section 06, type a title and a one-line note on what to look at, pick your name, pick the product, name the feature, Save.

Finding things. The pills above the list are the five names: All, Jillienne, Anjani, Eric, Afsana, Cody. Click a name to see only that person's rows; click it again to clear. There is no product pill any more; the product is the tag on the row. Rows sit under their feature heading, so looking for a piece of work means looking for its name rather than its branch.

When a row's discussion is over.

You want toDo thisWhat happens
Tidy it off the board but keep itClick the row's ⋮, choose ArchiveThe row disappears from the board. It is stamped with when and by whom. Nothing is deleted.

Use Archive by default. Remove is for mistakes.

Two things to know

The Updated tag changes only when the row is saved, not when your branch changes; if you push a big change, open the row and Save it again so the team sees fresh activity.

And a Refinement row follows main underneath: if a component you point at changes on main, the row changes with it. Anything that must stay frozen, a user test for instance, is Jillienne's /promote-to-testing, not a Refinement row.

There are two separate decisions, made by two different people:

  • What the surface should be is the owner's call, and the owner records it by running the promotion on their own branch.
  • When it reaches main is Jillienne's call, and only she can do it.

When your branch is what your surface should become:

  1. Make sure the branch is current (section 04, steps 4 to 8) and the review link looks right.
  2. On your branch, type /promote-to-prototype and name your scope: "for Compass" (Anjani), "for Atlas Learning" or "for Invite & Purchase" (Eric).
  3. Claude lists the flags your branch introduced and asks, for each, whether it should be the default. Say yes to the ones that are your design and no to anything experimental you are not ready to stand behind.
  4. It commits those defaults on your branch. Nothing has reached a stakeholder yet; this is a decision written down, not a release.
  5. "Push my branch."
  6. Tell Jillienne, in words: "My Compass branch feat/… is ready to ship." Include the review link.
  7. Jillienne runs /ship-to-main. It refuses a branch whose owner has not run step 2, so the order matters.
  8. A few minutes after she ships, your surface's row on Prototypes is your work. Its Updated tag changes to that moment.
  9. Archive your Refinement row (section 07), since the board is for things under discussion and this one is decided.
  10. Start the next piece from a fresh branch off main (section 06, step 1). Do not keep working on the shipped branch.

If you own the surface, you can also decide something should NOT go in. Say so, archive the Refinement row, and tell Jillienne; she has a routine that records why a branch was tried and declined.

12The morning auto-rebase

You can have Claude rebase your branch for you every weekday morning, so section 04 becomes something that happens while you get coffee. Claude Code has scheduled tasks: you describe the job once, and it runs it in your project folder on a schedule, in a fresh session, and sends you a note when it is done.

Two things to know before you set it up:

  • It runs while the Claude app is open. If your laptop was closed at 8:30, it runs the next time you open the app. In practice that means "when I start my day".
  • It works on whichever branch is checked out in your xcel-ux-dashboard folder. That is the branch you were on when you closed the app yesterday, which is almost always the one you want.

Set it up once. Open the Code tab on the project and paste this, exactly:

Create a scheduled task called morning-rebase that runs every weekday at 8:30 in this project folder. Each run, do the following and nothing else:

1. Report the current branch. If it is `main`, or there is no branch checked out, stop and say so.
2. If there are uncommitted changes, stop and say so. Do not stash them and do not commit them.
3. Fetch origin. If the branch is zero commits behind origin/main, report "already current" and stop.
4. Create a local backup branch named backup/‹branch›/‹today's date› pointing at the current commit. Do not push it.
5. Rebase the branch onto origin/main. If any file conflicts, abort the rebase so the branch is exactly as it was, and report which files conflicted and in which commit.
6. If the rebase succeeded, run `npm run build` and then `npx vitest run`. If either fails, do not push. Report what failed; say that the local branch is rebased but origin still has yesterday's version.
7. If both passed, push the branch to origin with `--force-with-lease`. Never push main. Never push without the lease.
8. Finish with a six-line summary: the branch; how many commits behind it was; whether there were conflicts; whether build and tests passed; whether it pushed; and the Netlify review link for the branch.

Never run `git switch main`, never edit files, never resolve a conflict yourself, and never delete anything.

Claude confirms the schedule and the task name. Say yes.

What you see each morning. A short note in the Claude app: rebased and pushed, or stopped and why. If it says it stopped on a conflict, do section 04 step 5 by hand. If it says checks failed, open the Code tab and say "Show me what failed in the morning rebase".
