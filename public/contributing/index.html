Contributing to the dashboard

Download as PDF ← Back to the dashboard

How to get your work in front of the team and then in front of stakeholders — from getting the project onto your computer to seeing your change land in Prototypes. Everything happens in the Claude desktop app: each step is a sentence you say to Claude. Nothing is typed into a terminal, and github.com is only opened once, to accept the invitation.

Last updated 21 September 2026 · Owner: Jillienne Moreno · Applies to jillmoreno/xcel-ux-dashboard

Part 1 · Quick walkthrough

The loop, in one picture

Left to right: you make a branch and Claude pushes your work to it, Netlify builds it at its own address, you paste that address into Refinement where the team sees it, a toggle shows it to stakeholders, and a PR plus the promote step lands it in Prototypes. Everything below is one of those boxes in detail.

Nine steps

1Get the project onto your computer

Once. Make an empty folder, open the Claude desktop app, connect that folder, and say "Clone the GitHub repository jillmoreno/xcel-ux-dashboard into this folder." Claude brings it down. You do not run the site locally — your preview is the branch build in step 5.

2Make a branch

Tell Claude "Make a new branch called feat/your-thing from main and switch to it." Name it feat/ plus two or three words, lowercase, joined with dashes. A branch is your own copy to work in — nothing on it changes what anyone else sees until it is merged.

3Build it with Claude

In the Claude desktop app, describe the work. Say which kind it is — a React surface (src/) or an HTML exploration (public/demos/) — and ask for a feature flag with its default on on your branch. Every so often: "Commit what we have so far."

4Ask Claude to run the checks

Before every publish, say "Run the type check, the tests and lint." Claude runs them and reports. A failing test is usually a recorded decision talking to you — ask Claude what it protects. Touched public/prototypes/? Add "and the smoke suites."

5Publish — that is the deploy

Say "Commit everything and push it to feat/your-thing." Claude sends it to GitHub; Netlify builds your branch as its own site. Share …/dashboard-rebrand?demo=1 so reviewers see your committed defaults. Every pushed branch gets an address — anyone with the link and the site password can open it.

6Add it to Refinement

On the full site: Refinement → Add link. Paste the address, title it with your branch name, say where to look. Leave Show on public site off.

Faster: in your Claude chat, say /promote-to-refinement. It works out the branch address, checks the push, drafts the title and note, and gives you a link that opens this form already filled in — you check it and click Add.

7Discuss and iterate

The team opens the row and talks. You change with Claude, ask for the checks, ask Claude to push again — the address stays the same, so the row stays right. Edit the row if its title or note should change.

8Flip it public

When it is ready for stakeholders, Jillienne (or you, once agreed) edits the row and ticks Show on public site. It appears on the public site's list, read-only. Untick to take it back — nothing is deleted.

9PR → promote → merge → retire

Tell Claude "Open a pull request from feat/your-thing to main and add Jillienne as reviewer." She runs promote-to-prototype on your branch — each flag your branch changed is kept on or set back to main's value — then merges. Both sites rebuild. Remove your Refinement row.

Four rules that cover most mistakes

Never push to main

Every push to main rebuilds the public site. Branch, then PR.

Promotion is a flag, not a tile

Prototypes holds exactly one row and a test guards it. Your work reaches it by a flag default flipping on main.

Review HTML goes in public/demos/

Both folders work on your branch build. public/demos/ is for work in review and is meant to be short-lived; public/prototypes/ is for a document that is becoming a permanent row. Only the second needs a row in the project list.

Every branch gets an address

Anyone with the link and the site password can open it — including work you are not ready to show. Nothing confidential on a branch.

Need the why behind any of these, the form field by field, or the troubleshooting table? Switch to the Full guide.

01The big picture

The dashboard is one codebase deployed to two websites. Every git push to main rebuilds both.

SiteWho opens it · what forWhat it shows
The full siteDesigners and developers.
Used for refinement and hand-offs.		Everything — Prototypes, Refinement, Other Links, Research, and the whole UX & Dev Access group (Design, Exploration, Sandbox, Development, Done, Archive, QA Notes, To Do, and this guide).
The public siteDesigners and stakeholders.
Used for demos and training.		Only Prototypes, Refinement, Other Links and Research. The rest is not locked — it is absent. Refinement shows only the rows someone has flipped to public, and is read-only there.

Two sections do the work of getting a design in front of people, and they are different acts:

  • Refinement is the review inbox. It is a list of links you add on the page — no code, no commit. A row points at your branch's own build (or an HTML file on it). The team sees every row; stakeholders see a row only after its Show on public site toggle is on.
  • Prototypes is the product as it stands — the live React build at the flag defaults committed on main. Only a merge to main changes it, and only Jillienne decides what merges into that baseline.

So the loop is:

branch→push→Refinement · Add link (or /promote-to-refinement)→team discusses→flip public→stakeholders→PR→promote→merge→retire the row

The rest of this guide walks each of those, in order, with the exact commands and the exact fields.

02What you need before you start

  • A GitHub account, with access to the project. Jillienne invites you; GitHub emails you; click Accept. To check it worked, open github.com/jillmoreno/xcel-ux-dashboard in your browser — if you see a list of files rather than a 404, you are in.
  • The Claude desktop app, with GitHub connected. In Claude: Settings → Connectors → GitHub → Connect, sign in to GitHub when it asks, and allow it. This is what lets Claude bring the project down to your computer and send your changes back up. Without it Claude can edit files but cannot talk to GitHub.
  • An empty folder on your computer for the project — for example Documents › xcel-ux-dashboard. Claude fills it in step 1.
  • The full site's address. Ask Jillienne.
You do not need

Terminal, Node, git, GitHub Desktop, or a Netlify account. Anything that would normally need a typed command, Claude does when you ask it in plain English. You never have to know what the command was.

03The nine steps

1Get the project onto your computer

You · once · in the Claude desktop app

What this is. The project lives on GitHub. To work on it, you need a copy in a folder on your own computer that Claude can see and edit. Getting that copy is called cloning, and Claude does it for you.

  1. Make an empty folder somewhere you will find it again — Documents › xcel-ux-dashboard is a good choice.
  2. Open the Claude desktop app and start a new chat. When it asks which folder to work in, choose the folder you just made. (If it does not ask, look for Connect a folder or the folder icon near the message box.)
  3. Type this and send it:
    "Clone the GitHub repository jillmoreno/xcel-ux-dashboard into this folder."
  4. Wait. Claude uses the GitHub connection to bring everything down. It takes a minute or two. Claude will tell you when it is done.
You are done when

The folder on your computer is no longer empty — you can see src, public, CLAUDE.md and a few dozen other things in it — and Claude has said the clone finished.

You do not run the site on your own computer. Older instructions talked about starting a local server at localhost:5200; that needs a terminal, so skip it. Your preview is the branch build Netlify makes in step 5 — a real web address you can open and send to people.

If Claude says it cannot reach GitHub, the connector is not connected — see What you need. If Claude says the folder is not empty, make a new empty one and connect that instead.

2Make a branch

You · every time you start a piece of work · one line to Claude

What a branch is, in plain words. The project has one official copy, called main. That is what both websites are built from. A branch is your own private copy of the project, with a name on it. You make your changes there. Nothing you do on your branch changes main — or either website — until Jillienne merges it in step 9. So you cannot break anything by working on a branch. That is the whole point of having one.

  1. Choose a name. The pattern is feat/ plus two or three words joined with dashes — for example feat/study-streak-card. All lowercase, no spaces. (Use explore/ for an exploration or fix/ for a fix; feat/ is right for most things.)
  2. Tell Claude. In the Claude desktop app, in your project chat, send:
    "Make a new branch called feat/study-streak-card from main and switch to it."
    Claude makes the branch on your computer and moves your folder onto it, so everything you do from here lands there. If the name breaks the rule, Claude will say so — accept its suggestion.
  3. Nothing to do on GitHub. The branch exists only on your computer until step 5. The first push creates it on GitHub, and from then on it has its own web address.
You are done when

Claude has confirmed it is on your branch. Ask "Which branch am I on?" any time you are unsure — the answer should never be main while you are working.

Why the name matters. In step 5 it becomes part of a web address, and the slash turns into a dash: feat/study-streak-card is reviewed at feat-study-streak-card--ux-design-xceldashboard.netlify.app. Spaces and capital letters would break that, which is why the rule is lowercase and dashes.

If something looks wrong

  • Claude says the name is not valid. There is probably a space or a capital letter in it. Lowercase, dashes only — take the corrected name Claude offers.
  • Claude says a branch with that name already exists. Someone (maybe you, earlier) already made it. Either say "Switch to it and bring it up to date" to carry on there, or choose a slightly different name.
  • You realise you have been working on main. Do not panic and do not push. Tell Claude: "I made changes on main by mistake — make a branch called feat/… , move my changes onto it, and leave main untouched." Claude moves your work across.
  • You want to pick up a branch you started on another computer. Say "Switch to the branch feat/… from GitHub and bring it up to date." Claude fetches it.

3Do the work with Claude

You · with Claude · in the desktop app

In your project chat, describe what you are building the way you would to a colleague. Claude edits the files in your folder. Three things make this go smoothly:

  • Tell Claude which kind of work it is — a React surface of the product, or a standalone HTML exploration. Section 04 explains the difference; it decides where the files go.
  • Ask Claude to put new product work behind a feature flag, and to set that flag's default on for your branch. Section 05 explains why. Claude knows the flag catalog (src/context/FeatureFlagContext.tsx).
  • Claude reads CLAUDE.md on its own — it is in the folder, and the app picks it up. It is the project's memory: every decision, every trap, every "we tried that and here is why not". A change that contradicts it will be questioned in review.

Save your progress as you go. Every so often, say: "Commit what we have done so far with the message 'study streak card on Home, behind a flag'." A commit is a labelled save point. Small ones with plain-English labels are easier for everyone to follow than one big one at the end. Nothing leaves your computer until step 5.

4Ask Claude to run the checks

You · before every publish

The project has three automatic checks — types, tests and code style. They are the same ones review runs, so green here means no surprises later. Say:

"Run the type check, the tests and lint, and tell me what fails."

Claude runs them in its own workspace (it takes a minute or two — there are about 800 tests) and reports back. If you edited anything under public/prototypes/, add "and the smoke suites" — those pages have their own checks.

A failing test is usually the project telling you a decision is recorded somewhere — for example, the nav order, or which rows sit on the public front door. Ask Claude what the failing test is protecting; it will read the test's comment and explain. If your change is meant to re-decide that, ask Claude to update the test in the same commit and say so in the message.

5Publish — that is the deploy

You ask · Claude sends · Netlify builds

What this is. So far your work is only on your computer. Pushing sends it up to your branch on GitHub. Claude does it through the GitHub connection. Say:

"Commit everything with the message 'study streak card on Home' and push it to feat/study-streak-card."

Claude confirms. Within a few seconds, Netlify notices the push and starts building your branch as its own website at:

https://feat-study-streak-card--ux-design-xceldashboard.netlify.app

That is your-branch-with-dashes followed by --ux-design-xceldashboard.netlify.app. The build takes two to three minutes. Every later push to the same branch updates the same address.

The link to share is the product, in demo mode:

https://feat-study-streak-card--ux-design-xceldashboard.netlify.app/dashboard-rebrand?demo=1

?demo=1 makes the page show your branch's committed flag defaults — what you set in step 3 — rather than whatever toggles the person opening it last left in their own browser. Without it, a reviewer may see their own leftover settings and think that is your design.

You are done when

Claude confirms the push went through, and two or three minutes later the address above opens and shows your work. (If you are curious, the branch is now visible at github.com/jillmoreno/xcel-ux-dashboard/branches — but you never need to look.)

Know this

Every pushed branch gets an address, and anyone with the link and the site password can open it — including work you are not ready to show yet. That is what makes review possible, and it is why nothing confidential goes on a branch.

A branch address is a copy of the whole dashboard, so it carries the team-only sections as well as your work. The house icon in the dark bar is hidden on branch builds for that reason — someone you send a review link to lands on your work, not on the project list.

If Claude says it cannot push, the GitHub connection is missing or has expired — Settings → Connectors → GitHub. If the address 404s after five minutes, ask Claude "What is the exact name of the branch I pushed?" and check the address uses it, dashes for slashes; then ask Jillienne to confirm branch deploys are on.

6Add it to Refinement

You · on the full site

Open the full site, click Refinement in the left nav, then Add link (or Add the first link if the list is empty). Paste the address from step 5, give it a title, and write a one-line note saying where to look. Leave Show on public site off. Section 06 has every field.

The row appears immediately for everyone on the full site. It is saved to a shared store, not to your browser, so the team sees it the moment you save.

The short way

In your project chat in the Claude desktop app, say /promote-to-refinement. The skill works out the branch address (dashes and all), confirms the branch is pushed and built, drafts the title from your commits, asks you for the one-line note, and gives you a link that opens the full site with the Add form already filled in. You click the link, look, and click Add link — nothing is saved without that click, and the public toggle stays off. Its twin, promote-to-prototype, is what Jillienne runs at the other end of the loop (step 9).

7Discuss, iterate, publish again

You and the team

The team opens your row, looks, and talks — wherever the team talks. You make changes with Claude (step 3), ask for the checks (step 4), and ask Claude to commit and push again (step 5). The address does not change, so the Refinement row is still right. If what the row is changes, use Edit on the row to update its title or note.

There is deliberately no comment thread on the row. Refinement is a list of things to look at, not a place to record the discussion; that stays where the team already talks.

8Flip it public when it is ready for stakeholders

Jillienne — or you, once agreed

Edit the row and switch Show on public site on. From that moment the row shows on the public site's Refinement list, read-only, and stakeholders with the public link can open your branch build. Switch it off again to take it back out — nothing is deleted.

The convention is that Jillienne flips it, because the public list is what stakeholders read as "what the team wants us to look at". If she has asked you to flip your own, go ahead.

9Open a pull request → promote → merge → retire the row

You open the PR · Jillienne promotes and merges

What a pull request is. It is the formal "please bring my branch into main" — a page on GitHub that shows every change, where Jillienne reviews and merges. You open it; she does the rest.

  1. Tell Claude. "Open a pull request from feat/study-streak-card to main, titled 'Study streak card', and add Jillienne as reviewer. In the description, put my Refinement note and the branch build address." Claude opens it through the GitHub connection and gives you the link.
  2. Open the link once to check the title and description read the way you want. That is the one page on github.com you will see in this whole loop, and you do not have to change anything on it.

If Claude says it cannot open a pull request, the GitHub connection may not have that permission — send Jillienne the branch name and the build address instead, and she will open it.

Jillienne then runs the promote-to-prototype skill on your branch, before merging. It lists every feature flag your branch changed and asks her, flag by flag, whether that default ships in Prototypes. Approved flags keep your "on"; declined ones are set back to main's value, so the work lands in the sandbox sections of the full site without reaching the public product.

She merges. Both sites rebuild. The last step is retiring your Refinement row — Remove on the row — because the thing it pointed at is now in Prototypes (or the branch is gone).

Done looks like

Your flag's default is on in main, the Prototypes section shows your work at /dashboard-rebrand?demo=1, and Refinement no longer lists your branch.

04Two kinds of work, two homes

Where files go depends on what you are making, and picking wrong is the most common mistake in this repo.

You are makingIt lives inReviewers openPromoted by
A React surface of the productsrc/ — a page in the shell, a card, a panel, a variant of an existing block. Behind a feature flag.<branch>--…netlify.app/dashboard-rebrand?demo=1Flipping the flag's default on main (the promote skill).
A standalone HTML explorationpublic/demos/<your-file>.html — a hand-authored page answering a brief, not wired into the app.<branch>--…netlify.app/demos/<your-file>.htmlMoving it to public/prototypes/ with a row in prototypeFeatures.ts if it is a finished exploration, or rebuilding it in src/ if it became a product surface.
Why public/demos/ and not public/prototypes/

The public site 404s everything under /prototypes/ at the edge — that folder holds the finished FinServ explorations, which are gated. A file there is invisible on your branch's public build too. public/demos/ is deliberately left open for exactly this: HTML in review. Nothing should live there long, and nothing there gets a row in the feature list — the Refinement panel is its listing.

05Feature flags — the one rule

Every change to the product starts invisible to Prototypes: behind a flag whose default on main is off (or set to the existing variant). That is what lets many designers work on the same product without anyone's half-finished idea appearing in front of stakeholders.

On your branch, you set that flag's default on. That is what makes your branch build show your work at ?demo=1. It also means the promote skill can see, mechanically, exactly which defaults your branch changed — the list it asks Jillienne about in step 9 is the diff of the flag catalog between your branch and main.

  • Flags live in src/context/FeatureFlagContext.tsx, in FEATURE_FLAGS. Ask Claude to add yours there and to add it to the /dashboard-rebrand panel scope so reviewers can toggle it.
  • Reviewers can flip flags live on your build: hover the prototype bar and find the robot icon, which opens the flag sheet. In demo mode those flips are temporary and reset on exit.
  • Do not promote by adding a row to Prototypes. That section holds exactly one row — the product build — and a test compares it in both directions, so a second row fails the suite.

06The Refinement form, field by field

This is what Add link opens on the full site.

Refinement · Add link
AddressThe full https://… link. Required. Only http and https addresses are accepted — anything else is refused, on purpose, because every address here is rendered as a real link for everyone.
TitleWhat it is, in a few words. Required. Include the branch name so the row can be matched to a PR later: “Study streak card — feat/study-streak-card”.
NoteOptional, but use it. Say where to look and what question you want answered: “Home, under Current Progress. Is the streak motivating or nagging?”
Added byYour name. Optional; remembered in your browser so you type it once. It is a label, not a login — nothing checks it.
Show on public siteA checkbox, off by default. The hint under it reads: “Off: only the team sees this row. On: stakeholders with the public link see it too.”

On the list, each row carries a chip — Team only or Public — so you can see at a glance what stakeholders can see. The nav badge on Refinement counts all rows on the full site and only the public ones on the public site.

There is no Type field here, unlike Other Links. Every Refinement row is the same kind of thing — work in review — and the toggle is what tells rows apart.

07Things not to do

  • Don't push to main. Every push to main rebuilds the public site. Always be on a branch before asking Claude to push — step 2 — and get to main only through a pull request.
  • Don't add a row to Prototypes or change a row's category to 'prototype'. Promotion is a flag default, never a tile move.
  • Don't put review HTML in public/prototypes/. It is 404'd on the public build. Use public/demos/.
  • Don't change a flag's default on main yourself. That is the promote step, and it is Jillienne's call.
  • Send your branch build, never the main dashboard. Your branch address shows your work; the main address shows what is already decided, and everything else the team is doing.
  • Don't invent data. A number, a URL, a lesson count or a fee that XCEL has not published is flagged as INVENTED in the code and named as such on screen. CLAUDE.md records why, several times over.
  • Don't draft the Quick Summary on a dev-handoff component — ask Jillienne for it. The dev-handoff-notes skill says the same.
