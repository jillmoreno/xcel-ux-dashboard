Part 1 · Quick walkthrough

The loop, in one picture

Left to right: you push a branch, Netlify builds it at its own address, you paste that address into Refinement where the team sees it, a toggle shows it to stakeholders, and a PR plus the promote step lands it in Prototypes. Everything below is one of those boxes in detail.

Nine steps

1Clone and run

Once. Download the project, install it, run it. Port 5200 — the sibling dashboards use 5180 and 5190 and look identical, so a wrong port shows the wrong project with no error.

2Make a branch

Your own line of work. git checkout -b feat/your-thing. Lowercase, dashes, a short prefix. The name becomes a web address in step 5 — slashes turn into dashes there.

3Build it in Claude Code

Say which kind of work it is — a React surface (src/) or an HTML exploration (public/demos/) — and ask for a feature flag with its default on on your branch. Let Claude read CLAUDE.md first.

4Run the checks

Before every push. A failing test is usually a recorded decision talking to you — read its comment. If you touched public/prototypes/, add npm run smoke.

5Push — that is the deploy

Netlify builds every pushed branch as its own site, no password. Share …/dashboard-rebrand?demo=1 so reviewers see your committed defaults, not their own leftover toggles. Branch addresses are not private.

6Add it to Refinement

On the full site: Refinement → Add link. Paste the address, title it with your branch name, say where to look. Leave Show on public site off. Saved to a shared store — the team sees it at once.

7Discuss and iterate

The team opens the row and talks. You change, check, push — the address stays the same, so the row stays right. Edit the row if its title or note should change.

8Flip it public

When it is ready for stakeholders, Jillienne (or you, once agreed) edits the row and ticks Show on public site. It appears on the public site's list, read-only. Untick to take it back — nothing is deleted.

9PR → promote → merge → retire

Open a PR. Jillienne runs promote-to-prototype on your branch — each flag your branch changed is kept on or set back to main's value — then merges. Both sites rebuild. Remove your Refinement row.

Four rules that cover most mistakes

Never push to main

Every push to main rebuilds the public site. Branch, then PR.

Promotion is a flag, not a tile

Prototypes holds exactly one row and a test guards it. Your work reaches it by a flag default flipping on main.

Review HTML goes in public/demos/

public/prototypes/ is 404'd on the public site — a file there is invisible on your branch build too.

Branch addresses are public

Anyone with the link can open one. Nothing confidential on a branch.

Need the why behind any of these, the form field by field, or the troubleshooting table? Switch to the Full guide.

01The big picture

The dashboard is one codebase deployed to two websites. Every git push to main rebuilds both.

SiteWho opens itWhat it shows
The full siteYou, Jillienne, the team. Behind a Netlify password.Everything — Prototypes, Refinement, Other Links, Research, and the whole UX & Dev Access group (Design, Exploration, Sandbox, Development, Done, Archive, QA Notes, To Do, and this guide).
The public siteStakeholders, with the link. No password.Only Prototypes, Refinement, Other Links and Research. The rest is not locked — it is absent. Refinement shows only the rows someone has flipped to public, and is read-only there.

Two sections do the work of getting a design in front of people, and they are different acts:

  • Refinement is the review inbox. It is a list of links you add on the page — no code, no commit. A row points at your branch's own build (or an HTML file on it). The team sees every row; stakeholders see a row only after its Show on public site toggle is on.
  • Prototypes is the product as it stands — the live React build at the flag defaults committed on main. Only a merge to main changes it, and only Jillienne decides what merges into that baseline.

So the loop is:

branch→push→Refinement · Add link→team discusses→flip public→stakeholders→PR→promote→merge→retire the row

The rest of this guide walks each of those, in order, with the exact commands and the exact fields.

02What you need before you start

  • Access to the GitHub repo jillmoreno/xcel-ux-dashboard with permission to push branches. Ask Jillienne if you cannot see it.
  • Node.js 20 or newer and git installed. Check with node -v and git --version in Terminal.
  • Claude Code, for working in the repo. The repo carries its own instructions (CLAUDE.md) and skills (.claude/skills/), so a fresh Claude Code session already knows the project's rules.
  • The full site's address and password. Ask Jillienne — it is not written down here on purpose.
You do not need

A Netlify account, any deploy tooling, or to know how the two sites are configured. Pushing a branch is the deploy. Everything else is set up once, centrally, and described in the README for whoever maintains it.

03The nine steps

1Clone the repo and run it

You · once

Clone means "download the project as a git repository". You do this once; after that you pull updates rather than re-downloading.

git clone https://github.com/jillmoreno/xcel-ux-dashboard.git
cd xcel-ux-dashboard
npm install
npm run dev

Open http://localhost:5200. You should see the dashboard. The port is 5200 on purpose — the sibling dashboards use 5180 and 5190, and they look alike, so a wrong port shows you the wrong project with no error.

Refinement and Other Links will say their endpoint is unreachable when you run npm run dev. That is expected — those two lists live on Netlify, and plain vite does not serve them. You add rows on the full site, not locally.

2Make a branch

You · every piece of work

A branch is your own copy of the code to work on. Nothing you do on it touches what anyone else sees until it is merged.

git checkout main
git pull
git checkout -b feat/study-streak-card

Naming: lowercase, words joined with dashes, a short prefix that says what kind of thing it is — feat/, explore/, fix/. The branch name becomes part of a web address in step 5, and slashes turn into dashes there, so feat/study-streak-card becomes feat-study-streak-card.

3Do the work in Claude Code

You · with Claude

Open the repo folder in Claude Code and describe what you are building. Three things make this go smoothly:

  • Tell Claude which kind of work it is — a React surface of the product, or a standalone HTML exploration. Section 04 explains the difference; it decides where the files go.
  • Ask Claude to put new product work behind a feature flag, and to set that flag's default on for your branch. Section 05 explains why. Claude knows the flag catalog (src/context/FeatureFlagContext.tsx).
  • Let Claude read CLAUDE.md first. It is the project's memory — every decision, every trap, every "we tried that and here is why not". A change that contradicts it will be questioned in review.

Commit as you go. Small commits with plain-English messages are easier for everyone to follow than one big one at the end.

git add -A
git commit -m "feat: study streak card on Home, behind dashboard-study-streak"

4Check it before you push

You · before every push

Run the three checks. They are the same ones review will run, so a green result here means no surprises later.

npx tsc -b --noEmit     # types
npx vitest run          # the test suite (~800 tests, about a minute)
npm run lint            # code style

If you edited anything under public/prototypes/, also run npm run smoke — those pages have their own suites and vitest does not run them.

A failing test is usually the suite telling you a decision is recorded somewhere — for example, the nav order, or which rows sit on the public front door. Read the test's comment; it will say what was decided and why. If your change is meant to re-decide it, update the test in the same commit and say so in the message.

5Push — that is the deploy

You · Netlify does the rest

git push -u origin feat/study-streak-card

Netlify notices the new branch and builds it as its own website, with no password, at:

https://feat-study-streak-card--ux-demo-xceldashboard.netlify.app

That is <your-branch-with-dashes>--ux-demo-xceldashboard.netlify.app. The build takes two to three minutes. Every later push to the same branch updates the same address.

The link to share is the product, in demo mode:

https://feat-study-streak-card--ux-demo-xceldashboard.netlify.app/dashboard-rebrand?demo=1

?demo=1 makes the page show your branch's committed flag defaults — what you set in step 3 — rather than whatever toggles the person opening it last left in their own browser. Without it, a reviewer may see their own leftover settings and think that is your design.

Know this

A branch address is not private. Anyone who has it can open it, and every pushed branch gets one. That is what makes stakeholder review possible without a password — and it is why nothing confidential goes on a branch.

6Add it to Refinement

You · on the full site

Open the full site, click Refinement in the left nav, then Add link (or Add the first link if the list is empty). Paste the address from step 5, give it a title, and write a one-line note saying where to look. Leave Show on public site off. Section 06 has every field.

The row appears immediately for everyone on the full site. It is saved to a shared store, not to your browser, so the team sees it the moment you save.

7Discuss, iterate, push again

You and the team

The team opens your row, looks, and talks — wherever the team talks. You make changes on the branch, run the checks, push. The address does not change, so the Refinement row is still right. If what the row is changes, use Edit on the row to update its title or note.

There is deliberately no comment thread on the row. Refinement is a list of things to look at, not a place to record the discussion; that stays where the team already talks.

8Flip it public when it is ready for stakeholders

Jillienne — or you, once agreed

Edit the row and switch Show on public site on. From that moment the row shows on the public site's Refinement list, read-only, and stakeholders with the public link can open your branch build. Switch it off again to take it back out — nothing is deleted.

The convention is that Jillienne flips it, because the public list is what stakeholders read as "what the team wants us to look at". If she has asked you to flip your own, go ahead.

9Open a pull request → promote → merge → retire the row

You open the PR · Jillienne promotes and merges

When the work is agreed, open a pull request from your branch to main on GitHub. Jillienne then runs the promote-to-prototype skill on your branch, before merging. It lists every feature flag your branch changed and asks her, flag by flag, whether that default ships in Prototypes. Approved flags keep your "on"; declined ones are set back to main's value, so the work lands in the sandbox sections of the full site without reaching the public product.

She merges. Both sites rebuild. The last step is retiring your Refinement row — Remove on the row — because the thing it pointed at is now in Prototypes (or the branch is gone).

Done looks like

Your flag's default is on in main, the Prototypes section shows your work at /dashboard-rebrand?demo=1, and Refinement no longer lists your branch.

04Two kinds of work, two homes

Where files go depends on what you are making, and picking wrong is the most common mistake in this repo.

You are makingIt lives inReviewers openPromoted by
A React surface of the productsrc/ — a page in the shell, a card, a panel, a variant of an existing block. Behind a feature flag.<branch>--…netlify.app/dashboard-rebrand?demo=1Flipping the flag's default on main (the promote skill).
A standalone HTML explorationpublic/demos/<your-file>.html — a hand-authored page answering a brief, not wired into the app.<branch>--…netlify.app/demos/<your-file>.htmlMoving it to public/prototypes/ with a row in prototypeFeatures.ts if it is a finished exploration, or rebuilding it in src/ if it became a product surface.
Why public/demos/ and not public/prototypes/

The public site 404s everything under /prototypes/ at the edge — that folder holds the finished FinServ explorations, which are gated. A file there is invisible on your branch's public build too. public/demos/ is deliberately left open for exactly this: HTML in review. Nothing should live there long, and nothing there gets a row in the feature list — the Refinement panel is its listing.

05Feature flags — the one rule

Every change to the product starts invisible to Prototypes: behind a flag whose default on main is off (or set to the existing variant). That is what lets many designers work on the same product without anyone's half-finished idea appearing in front of stakeholders.

On your branch, you set that flag's default on. That is what makes your branch build show your work at ?demo=1. It also means the promote skill can see, mechanically, exactly which defaults your branch changed — the list it asks Jillienne about in step 9 is the diff of the flag catalog between your branch and main.

  • Flags live in src/context/FeatureFlagContext.tsx, in FEATURE_FLAGS. Ask Claude to add yours there and to add it to the /dashboard-rebrand panel scope so reviewers can toggle it.
  • Reviewers can flip flags live on your build: hover the prototype bar and find the robot icon, which opens the flag sheet. In demo mode those flips are temporary and reset on exit.
  • Do not promote by adding a row to Prototypes. That section holds exactly one row — the product build — and a test compares it in both directions, so a second row fails the suite.

06The Refinement form, field by field

This is what Add link opens on the full site.

Refinement · Add link
AddressThe full https://… link. Required. Only http and https addresses are accepted — anything else is refused, on purpose, because every address here is rendered as a real link for everyone.
TitleWhat it is, in a few words. Required. Include the branch name so the row can be matched to a PR later: “Study streak card — feat/study-streak-card”.
NoteOptional, but use it. Say where to look and what question you want answered: “Home, under Current Progress. Is the streak motivating or nagging?”
Added byYour name. Optional; remembered in your browser so you type it once. It is a label, not a login — nothing checks it.
Show on public siteA checkbox, off by default. The hint under it reads: “Off: only the team sees this row. On: stakeholders with the public link see it too.”

On the list, each row carries a chip — Team only or Public — so you can see at a glance what stakeholders can see. The nav badge on Refinement counts all rows on the full site and only the public ones on the public site.

There is no Type field here, unlike Other Links. Every Refinement row is the same kind of thing — work in review — and the toggle is what tells rows apart.

07Things not to do

  • Don't push to main. Every push to main rebuilds the public site. Work on a branch; get there through a PR.
  • Don't add a row to Prototypes or change a row's category to 'prototype'. Promotion is a flag default, never a tile move.
  • Don't put review HTML in public/prototypes/. It is 404'd on the public build. Use public/demos/.
  • Don't change a flag's default on main yourself. That is the promote step, and it is Jillienne's call.
  • Don't paste a stakeholder the full site's address. They cannot open it, and the password is the team's. The review link is your branch build on the public site's domain.
  • Don't invent data. A number, a URL, a lesson count or a fee that XCEL has not published is flagged as INVENTED in the code and named as such on screen. CLAUDE.md records why, several times over.
  • Don't draft the Quick Summary on a dev-handoff component — ask Jillienne for it. The dev-handoff-notes skill says the same.

SymptomLikely causeTry
Branch address 404sNetlify hasn't finished the build, or branch deploys were switched off.Wait three minutes and reload. If it still fails, check the branch name has slashes turned to dashes; then ask Jillienne to confirm branch deploys are on.
Branch shows old main, not your workYour flag default is off on the branch, or you opened the page without ?demo=1.Add ?demo=1. Then check FEATURE_FLAGS on your branch has your flag's default on.
The demo looks different on one laptop onlyThat browser holds a saved "Set as default" flag snapshot, which wins over the committed default per key.In that browser's DevTools → Application → Local Storage, delete cgp.featureFlags.customDefaults.
Refinement says "endpoint unreachable"You are on npm run dev locally, which serves no /api/*.Add rows on the full site, not locally. (netlify dev works locally but needs setup; see .claude/launch.json.)

09Glossary

RepoThe project's code, in git. jillmoreno/xcel-ux-dashboard on GitHub.
CloneDownload the repo to your machine, once.
BranchYour own line of work inside the repo. Nothing on it is public until merged — but its build has a public address.
PushSend your commits to GitHub. Netlify builds every pushed branch.
Branch deployThe website Netlify builds for one branch: <branch>--ux-demo-xceldashboard.netlify.app.
?demo=1Demo mode: render the committed flag defaults, ignore the viewer's own saved toggles, don't persist flips.
Feature flagA named switch in FEATURE_FLAGS. Off on main until promoted; on on your branch so your build shows it.
PrototypesThe section holding the live product build at main's flag defaults. One row. Changed only by merging.
RefinementThe review inbox: links added on the page, team-only until flipped public. Its internal id is demo — you will see that in URLs (?section=demo) and code.
Other LinksEverything else that lives elsewhere: briefs, boards, Figma files. Also added on the page.
PromoteJillienne's step on your PR: decide per flag whether its "on" default ships in Prototypes. Skill: promote-to-prototype.
Full site / public siteThe password-protected everything site, and the passwordless stakeholder site. Same code; one build-time switch.
